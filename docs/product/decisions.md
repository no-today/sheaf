# 产品决定

只写现在有效、从代码里看不出为什么的选择。技术取舍在 `docs/agent/architecture.md`。

## 术语

- **工作目录**：界面一律这样叫，只在解释 git 时写 worktree。
- **阅读差异时手动更新**：需求差异和独立未提交差异在可见时保留已加载内容，相关工作目录或 Git 索引变化后显示常亮的更新提醒，用户点击才重读。提醒期间未加载文件等待刷新，避免新旧内容混杂。离开差异页签、切换需求或窗口完全不可见后自动更新；仅失去焦点但仍可见不算离开。空白页没有阅读内容，直接更新。
- **主分支**：各仓库自己的 master、main 等（代码里叫 base）。
- **界面用日常说法，名称 2–4 字，说明不超 20 字**：保留开发者熟悉的提交、分支、合并、冲突、暂存、MR/PR、正则；其余换成白话：需求是「关注」，仓库是「包含」，git 未跟踪的文件是「新文件」，改动对比的目标是「对比分支」，合并流程的一段是「阶段」、最后一段是「终点分支」，快进收藏分支是「更新分支」，fetch 是「刷新远端」，origin 是「远端」，HEAD 是「上次提交」，丢弃改动是「还原」，命令日志是「操作记录」，索引是「数据」。同一个词只指一样东西。英文同一套对应：Follow、Include、New file、Compare branch、Stage、Final branch、Update Branches、Refresh Remotes、remote、Last commit、Discard、Activity log、Data。

## 界面方针

- Git 操作的界面和交互参照 IDEA，视觉参照 Zed：界面用系统字体，代码、分支、需求号和哈希用等宽字（默认内置 Geist Mono，可在设置里换），语法着色只用正文、关键字、字符串和注释四种色调；发丝线分区、无圆角、不用彩色强调，只有深色主题。
- 语言默认跟随系统（不是中文就用英文），也可在设置里指定。
- 没实现或此刻用不上的动作不显示，不置灰：只有一处改动就没有改动导航。
- 动效只回应用户的操作，不超过 140 毫秒，不循环，也不用于数据到达；系统要求减少动态效果时不动。
- 文字对比度有下限，由测试锁住，不靠肉眼：层级靠这几档灰度，既不能看不清，也不能挤成一档。
- 配置尽量在用的地方直接改，所见即所得。
- **失败不静默**：某个仓库读取失败时，其余仓库照常可用，失败的仓库在设置页、提示和 CLI 结果里点名，并保留上次读到的历史。工作区配置读不出时，原文件改名备份（`workspace.json.broken-时间`），用默认配置打开并提示备份位置，不覆盖原文件；CLI 遇到损坏的配置直接报错，不做备份。

## 需求页

- **差异分三种用途**：默认「全部改动」看需求全部改动：共同祖先到需求分支的已提交差异；「待合 阶段名」按合并流程阶段（每个阶段一项，名字取自配置）检查当前需求尚未进入该阶段的提交补丁，补丁等价算已合入，新增又删除的文件也保留提交过程。全部改动、待合阶段在每个仓库已提交改动之后列未提交文件；未提交模式只看未提交，均为关联 worktree 的 HEAD 到工作区，含暂存、未暂存及未跟踪。未提交信息、位置和文件数与仓库名放在同一条吸顶标题中，不另起说明行；左下仓库入口定位到该仓库在当前范围内的首个文件。前两种模式的页签文件数及增删行数只计已提交部分。独立改动窗口沿用打开项的比较范围。查看模式不修改合并流程或左侧进度。
- **需求分支必须包含完整需求号**：本地或远程分支都按名称匹配，不再从长期分支或接收合并的分支推断归属，手选也遵守同一限制。命名工作目录有未提交改动时，即使还没有带需求号的提交，也列入需求详情，全部改动、未提交及适用的待合阶段均可查看。找不到命名分支时，仍用该需求在此仓库的全部相关提交检查合并覆盖；无自己的提交可供判断时显示「无法确认」。保留提交历史，但不参与任何差异模式、文件数或行数统计。
- **提交数和文件数同口径**：都只算分支上不在基准里的提交；合并提交分两类：自动合并就能得到同样结果的（同步主分支）文件不计、提交页默认隐藏；合并时动过手的（解决冲突或顺手改了别的）标「手动合并」，默认显示，它改的文件进文件列表和文件数，差异看它相对重新合并的结果。分类在页面出来后补上，按提交哈希缓存在内存里。
- **合并流程属于工作空间，全部仓库共用**：默认阶段为开发中、待合 main、已合完、已归档。流程阶段可命名、指定目标分支、增删和重排，最后一个阶段是终点分支；目标分支留空时使用各仓库已配置的主分支。未自定义且未保存过 release 时，只有一个阶段，名称取已有 master 设置或 main，目标取 master 设置（留空使用各仓库主分支）；显式保存过 release 的旧配置保留 release、master 两阶段，已保存的自定义流程不变。仓库不存在的中间阶段自动跳过，也可为仓库设置只看终点；终点分支不存在不能判为已合并。阶段差异跳过不适用的仓库。合入后面的阶段即可越过前面的阶段。未提交只指需求分支上的未提交改动；已提交但未推送仍按合并进度判断。需求分支的未提交改动还没读到时（刚打开工作空间），该仓库和需求显示「读取中」，读到后再定阶段，不先按提交显示待合；读取失败按没有未提交处理。需求取各仓库最早阶段，无法确认的仓库会挡住「已合完」，不能用已完成的仓库盖住尚未完成的仓库。归档只管理名单，独立保留按当前证据计算的合并进度，不表示已经合完。
- **合并进度按需求自己的提交判**：阶段检查需求命中的提交，不受页面对比范围过滤。非合并提交和确实引入父提交之外增删的合并提交计入需求改动。选择父提交已有内容、只增删冲突标记的合并不重复算需求改动，但仍保留在提交和差异中；干净的同步合并不算，没分类的合并提交也不算。目标分支「覆盖」提交是指它是那条线的祖先，或线上有补丁等价的非合并提交（`git patch-id --stable` 相同，含 cherry-pick、单提交 squash）。多个提交压成一个、被后续 Revert 抵消、合入时改过内容的移植，认不出来。整条分支的头、分支上别的需求不影响判定；个人长期分支上的未提交改动不归任何需求；只靠工作目录分支名发现的需求，干净时不出现。
- **需求号写法是工作区设置，默认 Jira 式 `[A-Z][A-Z0-9]+-\d+`（如 `ABC-123`、`AB2-7`）**：各团队编号不同，可在「我的提交」中改写法；来源只有工作目录分支名和我的提交标题，合并提交标题不算，否则同步合并会把别人的需求算进来。
- **改动连成一条流从上往下读，不先选文件**：把关看的是需求给 master 带来的全部改动，逐个点文件太慢。流按仓库分段，只读看得见的文件，超过 400 行的文件先折起来，任何文件都可点标题前的箭头手动折叠或展开；窗口够宽时旁边是目录，用来跳。否决文件树加单文件差异面板。全部改动按净差异过滤，加了又删、改了又改回的不列；已合入的行没有分支净差异，只去掉加了又删的。长文件滚动时文件头吸在仓库标题下面。
- **「未提交」入口覆盖全部未提交工作**：列出全部未提交目录，并标出归属的需求，便于统一检查工作区。归属沿用需求页的分支匹配规则，已归档仍算关注；命中多个关注号时取名单里靠前的号。个人长期分支、主分支以及只带未关注需求号的目录不标归属，不保留手动认领配置。
- **打开时显示最近的需求**：没有指定要看什么时，先显示左栏第一个关注中的需求；没有关注的需求时，有未提交改动就显示「未提交」，否则显示空页。
- **批量操作作用于全部可用的行，排除在确认窗里做**：页面上不再有勾选框，确认窗本来就能取消勾选。
- **MR 的目标使用对比分支**：切换查看模式或阶段不改变 MR 目标。
- **已合并且仍存在的分支可回看**：需求页列分支合并时自己的提交（靠合并提交定位）。同需求号的工作目录仍有未提交文件时，仓库行和需求整体都显示未提交；工作目录干净后恢复按合并进度显示。快进合并分不清分支范围，查不到；部分合并只看未合部分；手选分支的行按所选分支算。需求分支已删除时仅保留提交历史，不再回退到逐提交差异。
- **更新分支取收藏，不单独配置**：dev、uat、main 这类分支各团队叫法不同，收藏已经是「我常用的线」，再加一份配置只会重复。只快进本地分支。
- **用 glab / gh 创建 MR / PR**：按 origin 的主机分派，github.com 用 gh，其余用 glab；令牌和多主机归这两个命令行管，应用不存凭据。否决直接调 API（要自己管令牌）和打开 compare 网页（批量时一行一个标签页）。
- **glab 配置目录默认留空，沿用系统登录**：强制按工作区隔离会让所有人重新登录，而多数人只有一个账号。
- **只关注我输入的需求号**：左栏只列关注名单里的号，名单存在工作区配置里，只有用户动手才变（输入、点「关注」、「取消关注」，取消有 5 秒撤销）；自动发现（工作目录分支名、近 90 天我的提交标题）只当输入查找框时的「可关注」候选，不进列表，也不算阶段。名单里的号哪儿都没命中也照常列出（未提交、0 个仓库）。看一个没关注的号只是临时打开，不入名单。不再显示、编辑或保存筛选器，也不再读旧的 `tags.json`（不迁移，磁盘上的文件不动）；查找框按提交信息打开的结果只作为唯一的临时条目。
- **合并完成不自动归档**：已合完的需求继续显示。归档是手动、可撤销的工作区状态，保留关注和名称，重开仍有效；恢复后重新计算合并阶段。只有已归档一组默认折叠成一行，查找或正在查看其中的需求仍显示；折叠状态不存盘。
- **需求可以重命名**：标题存在工作区配置里（需求号 → 标题），盖过从提交取的标题，清空即恢复自动；取消关注不删名字和归档状态，再加回来还在。
- **阶段先快后准**：页面先用索引里的祖先关系出列表，随后补丁等价在后台补完，有变化就重读左栏，选中的需求不换。
- **忽略仓库在设置里**：按仓库开关，已忽略的仍列出以便打开；不做置顶和排序。

## 写操作的安全

- **应用目录外只允许安装命令行链接**：例外是 `/usr/local/bin/sheaf` 和 `/usr/local/share/zsh/site-functions/_sheaf` 两个符号链接，只由用户在设置 › 通用安装或卸载；只替换或删除指向 `Sheaf.app/Contents/Resources/` 下同名资源的自有链接，不覆盖其他文件或链接。
- 能写什么收窄到一张由测试锁住的白名单。应用只做刷新远端、更新分支（只快进）、创建 MR，以及在「未提交」页还原单个文件的未提交改动；工作目录留在原分支。可能产生冲突的合并交给 Coding Agent。
- 不强推，不自动 stash。除了用户在「未提交」页确认还原的那一个文件，不动有未提交改动的目录。还原只按字面路径动一个文件：已跟踪的恢复到 HEAD（暂存区和工作区一起），未跟踪的删除；合并、变基进行中不做。不备份，所以不给撤销，先确认。
- 弹窗和下拉框打开即是最终高度：内容（批量计划、分支列表）读完才打开，读的期间按钮不再响应，创建 MR/PR 按钮在计数位显示转圈；打开后不再出现会撑高的加载行或展开说明。
- 可撤销的用 Toast 给 5 秒撤销；更新分支和创建 MR 先列出命令再确认。刷新远端直接执行，不预览。较长的动作作为任务显示在状态栏右侧（仿 IDEA 后台任务），进度和每行结果看任务列表；提示框只用于失败、撤销和还原的结果。
- 操作记录只记写命令并存文件（目的是知道它在干什么、放心），不做界面页面。

## 名字

叫 Sheaf（一束）：一个需求散在各仓库的改动被扎成一束看。不用 MyGo：会让人以为是 mygo 官方出品，「X Git」也不在 Git 商标政策豁免之内。README 写 Built with mygo。

## 分发

没有付费 Apple Developer 账号，所以只有 ad hoc 签名、不公证：只支持 Apple 芯片，不出 Intel 版（CI 也只跑 arm64）。GitHub Releases 分发一个 `sheaf-<版本号>.dmg`；README 和站点链到 latest 发布页，不直链文件。CLI 和 zsh 补全随应用内置，只从设置 › 通用安装，不单独分发。README 写首次打开怎么过 Gatekeeper（系统设置「仍要打开」或 `xattr -dr com.apple.quarantine`）。不进 Homebrew 官方 cask（未签名的已被禁用）。以后有账号再签名公证。
