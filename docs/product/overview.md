# 产品定位

## 是什么

需求改动追踪器：按需求号把一个需求在几十个仓库和工作目录里的改动合成一处，开发中能审，发布后能回溯。给一个需求常散在多个仓库、分支名带需求号、改动多由 Coding Agent 写的人用；开源，不追求通用。

## 为什么

- 代码主要交给 Coding Agent 写：它从 `origin/master` 拉工作目录，分支名后缀带需求号，提交、合并也由它做。人只观察和把关。
- 公司的仓库多且合并不了，一个需求常常散在多个仓库、多个工作目录里，要能一眼看全。
- 把关的时机随需求的分量而定：支付这类不可逆的，没提交就要看；中等的，合并进 master 前看；简单的交给测试，合并时扫一眼。三种看的是同一件事，即这个需求给 master 带来什么改动。
- 发布后还要能按需求号回到当时的改动，分支删了也一样。
- 小改动不值得单独拉分支，会落在个人的长期开发分支上；也有不带需求号的修复。

## 核心路径

1. 打开工作区，在需求页从左栏挑一个需求，看它在各仓库走到哪一步（对比 uat 或 master；uat 混着别人的分支，只用来回答进没进，不当改动的基准）。
2. 从上往下读它给 master 带来的全部改动，包括还没提交的。
3. 在提交页打开某个提交的独立改动窗口；冲突解决提交看它相对重新合并结果的改动。
4. 刷新远端、更新收藏分支、批量创建 MR。
5. 不启动 GUI，用独立 CLI 批量查看关注名单、按号查询历史提交、检查流程覆盖，并管理关注、归档和工作区配置；为 Coding Agent 提供稳定 JSON 与退出码。CLI 与 GUI 共用 session 判定和数据目录，默认只读本地 Git，显式 `--fetch` 才刷新远端。覆盖通过不代表审批、部署或功能仍然生效。

## 明确不做

- CLI 中执行合并、更新分支、创建 MR/PR、提交或代码差异渲染；调查代码仍使用原生 Git。
- 单仓库的 Git 客户端：提交窗口、pull、变基、分支菜单、冲突解决。这些交给 Coding Agent 和终端。
- 通用的单仓库或 GitHub/GitLab 全功能客户端：只做按需求号看改动和少量批量写操作。
- stash / shelve，切分支时自动 stash。
- 强推：被拒就照实报，由人在终端处理。
- 对外的插件系统。
- 逐个文件标「已看」的把关台，以及「上次看过之后的增量」：AI 改动量大，人不会看完。
- 把仓库合成 monorepo。

## 还没做

- **提交约定**：`docs/templates/agent-commit-convention*.md` 是给 Coding Agent 的模板（分支名带需求号、提交标题以需求号开头），Agent 读了就能自己配置到工作区；应用不检查是否遵守。`docs/templates/githooks/dispatch` 是可选的本机 hook，按同一约定检查提交标题，缺编号时按分支名补上。
